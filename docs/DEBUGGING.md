# Debugging and logging

The app explains itself through its **session log**; a symptom that is not in the log gets a log event before it
gets a theory. This file says what the log holds, how to get it, and how bug reports flow from a shake on the
phone to a closed issue. The test rungs are in [TESTING.md](TESTING.md); the analysis rules in
[analysis/](analysis/README.md).

## The session log

- One file per launch: `Documents/logs/swing-<yyyyMMdd-HHmmss>.jsonl` in the app container, visible in the Files
  app. Writer: [`ExerciseAnalyzer/SessionLog.swift`](../ExerciseAnalyzer/SessionLog.swift).
- JSON Lines, one event per line: `{"type": "<event>", "t": <ms since launch>, ...fields}`. Numbers stay numbers,
  never strings; booleans may be logged as 0/1 by older events.
- The watch app cannot write to the phone's file, so it forwards its own events (`watch_<type>`, with `watch_t` as a
  wall-clock stamp) over WatchConnectivity; they land in the phone's log when the link is up.
- At launch, after the new session's log is open, the app deletes `logs/*.jsonl` older than 30 days, except any
  file named by a report in `bugs.jsonl`, and logs one `logs_pruned` event (count, bytes freed, kept_for_reports)
  even when zero (#72).

```bash
just pull-logs                  # phone → ~/tmp/agent/swing-logs/ (logs/, bugs.jsonl, bugs/<stamp>/ images)
just pull-logs-sim              # simulator → ~/tmp/agent/swing-logs/sim/
just log-summary <file.jsonl>   # everything except per-frame events, plus the frame count
jq -c 'select(.type!="frame")' <file>                         # the same, raw
jq -c 'select(.type|test("watch|camera"))' <file>             # one subsystem
jq -c 'select(.t > 57000 and .t < 60000)' <file>              # around a moment (a report's session_t_ms)
jq -c 'select(.type=="watch_heartbeat" and .gap_ms > 2500)' <file>   # every hole in the wrist's heartbeat (#122)
```

`pull-logs` copies with `devicectl`; "No provider was found" lines are noise, and "socket was closed unexpectedly"
means the phone was busy or locked, so run it again. The current session's file is copied as it stands.

## Event catalogue

`workout_page` is also emitted when the displayed workout changes: `sets`, `reps`, `heart_rate_samples`,
`live`, `workout_id`, `duration_s`, and `window_s` describe the current render. A live page refreshes its clock
every 5 seconds while active (#308) and re-asks Health every 20; its moving end re-logs only at each 20 s step
from the workout's start, so it logs no more often than before; saving switches `workout_id` from `live` to the saved id.

## Bug reports: from a shake to a closed issue

1. **On the phone**: shake, ⌘I, or "Report a problem" in the log's ⋯ menu. The sheet is
   [BugKit](https://github.com/idvorkin/bug-kit)'s (shared with Context Grabber and Magic Monitor); this app supplies
   the hooks in `BugReport.swift`: the screen name, the context (exercise, playhead, reps, clip…, numbers as
   numbers), the session log's position and, in playback, the clip's frame at the playhead as `frame.jpg`. The
   moment is captured before the sheet appears (a window snapshot) and the sheet opens over whatever is up (#41).
   "Log it" writes a `bug_report` event and one line in `Documents/bugs.jsonl` (`id`, `reported_at` with ms, `app`,
   `build`, `commit` from `BugKitCommit`, `device`, `screen`, `note`, `log`, `session_t_ms`, `screenshot`, `folder`,
   `files`, `context`), with the images under `Documents/bugs/<stamp>/` (`-2`, `-3` within one second; the append
   is locked, so two reports never overwrite each other). "Log it and another" writes the same and empties the
   sheet; every report until the next shake carries that shake's picture (#212).
2. **The listener files it** (since 2026-10-11): bug-kit's `listener/bug-listener` is always on in a Herdr pane,
   polling every five minutes every paired iPhone and iPad; `~/.config/bug-kit/apps.json` names this app, its
   bundle, its repo and its tracker (GitHub, `idvorkin/exercise-analyzer`). Each poll copies new reports and crash
   files to `~/tmp/agent/bugs/exercise-analyzer/<device>/`, files one issue per report with the note, the context
   table (screen, clip, exercise, playhead, reps, build and commit, the log and its millisecond) and the
   screenshot's and frame's paths on the Mac, named and never posted to GitHub (they reach the Mac only through
   the private CloudKit container `iCloud.com.idvorkin.BugKitReports`, Igor's own iCloud in the Development
   environment, or the device pull; the repo is public; BugKit principle 13;
   the markers `<!-- bug:<reported_at> -->` and `<!-- bug-id:<id> -->` make filing idempotent), then appends a line
   to `~/tmp/agent/bugs/inbox.jsonl` (`t`, `app`, `device`, `key`, `kind`, `reported_at`, `note`, `ref` the issue
   URL, `dir`) and sends a Herdr notification. Nobody else files: `just file-bugs` is the fallback for a listener
   that is down, and next to a live one it files the same report twice. A report that fails to copy or file stays
   pending for the next poll; `listener/bug-listener status --json` in the bug-kit checkout shows the last poll and
   what is pending. Through the app's `pull_extra` list in `apps.json` the listener also copies the
   WatchConnectivity inbox (`Documents/Inbox/com.apple.watchconnectivity/`, the watch's transfers waiting for the
   app, #197). Since the 2026-10-11 bug-kit bump the phone also uploads each report to the private CloudKit
   container `iCloud.com.idvorkin.BugKitReports` (BugKit's `CloudKitReportDelivery`, made in `BugReport.swift`,
   restarted on every foreground; not in the simulator), and the listener reads that container too
   (`cloudkit_config` in its config, the Mac reader app under `~/Applications/BugKitCloudReader.app`): a report
   from the gym is filed before the phone is back on the Wi-Fi. The log says what happened to the upload:
   `bug_delivery_queued`, `bug_delivery_uploading`, `bug_delivery_uploaded`, `bug_delivery_retry` (with the
   backoff), `bug_delivery_pending` (evidence missing or oversized, left to the device pull) and
   `bug_delivery_stopped` (a permanent error; needs attention).
3. **Monitor while Igor tests**: arm `scripts/bugs-monitor.sh` as a persistent `Monitor`. It tails the inbox and
   prints one line per issue the listener filed for this app (`filed <kind> <device> <issue url> <note>`), and it
   watches the listener itself: `listener_stale <age>` when `status.json` shows no poll started or completed for
   three intervals, `listener_missing` when there is no status at all, `listener_error <text>` when its last poll failed
   (`last_error` in `status.json`), `listener_ok` when it is back, so a dead or failing listener is not silence.
   It keeps the count of inbox lines it has read in `monitor-exercise-analyzer.lines` next to the inbox, so a
   re-arm first prints what was filed while no monitor ran; with no count yet it starts at the end, and an inbox

   ```
   Monitor(command: "scripts/bugs-monitor.sh", description: "issues the bug-kit listener filed for this app", persistent: true)
   ```

   `just bugs-check` (BugKit's `pull-reports.sh --check exercise-analyzer`: one stable line per report on a device

## Video frame descriptions

For video investigations, have a cheaper vision helper inspect the images and return text to the main agent.
Igor requested this on 2026-09-20 to reduce expensive image context. `CLAUDE.md` imports `AGENTS.md`, so the
same workflow applies to Codex and Claude.

1. Locate the exact source clip and pose track. Record the clip identity, duration and timestamp convention;
   filenames alone can collide in Photos. Extract local frames with timestamps in their filenames. Start with
   a small overview and add neighboring frames around candidate reps, setup, reracking and suspected mistakes.
2. Delegate a bounded batch to an available lower-cost model that accepts images. Give it a fresh context:
   frame paths, timestamps and the specific observation needed. Do not fork the main conversation's image
   history or have the main agent open the batch first. Keep the helper read-only in an isolated worktree.
   With the Codex tools available in this project, `gpt-5.6-luna`, `fork_turns="none"` and low reasoning are the
   starting choice for descriptions. Claude should select its own available cheaper vision model; OpenAI model
   IDs are not Claude configuration. If image input is unsupported, report that and select a compatible helper.
3. Request only observable facts: posture and movement across the supplied sequence, equipment, body parts
   outside the frame or hidden, confidence and remaining uncertainty. Return **text only**, with the timestamp
   and source path for every observation. Do not return images or base64 to the main agent. Distinguish a
   visible lunge position from evidence of a complete down-and-up rep; do not guess a count from sparse stills.
4. Cache the report under `~/tmp/agent/notes/`, keyed by source clip identity/content hash, frame timestamps,
   extraction settings, model and prompt version. Reuse matching observations instead of repeatedly sending
   the same frames. A changed crop, source, question or model may require a new observation.
5. The main agent compares those descriptions with the pose trace and failing fixture. If the evidence is
   unclear, send a denser local sequence or clearer frame to the helper first. Main-agent image inspection is
   limited to particular unresolved ambiguities or Igor's explicit request. Human count confirmation still
   belongs to Igor; use Lavish for that review and do not mark model-only counts `humanVerified`.

## Instruments from the command line

`just trace-device` attaches Instruments to the running app on the phone for 90 s with the Allocations template

## Crash reports

The app has no crash service; it uses MetricKit, which hands an app its own crash and hang diagnostics on the
next launch (BugKit's `CrashReports`, installed by the session once its log is open). Each payload is written to `Documents/crashes/<stamp>.json` and announced in
the new session's log as `crash_report` (kind crash or hang, exception type, signal, termination reason, the file).
MetricKit can take days on a development build, so the app also keeps its own last-resort files in the same folder:
`signal-<epoch>.txt` from a signal handler (the crashing thread's raw backtrace) and, for an Objective-C
exception, `exception-<epoch>.txt` with the exception's name, reason and symbolized stack (#87; the 2026-09-13
crash was an AVFCapture exception whose reason the signal file could not carry). Each is announced once as
`crash_report` (kind signal or exception) and renamed `.reported.txt`.
`just pull-logs` copies the folder; `just symbolicate ~/tmp/agent/swing-logs/crashes/<stamp>.json` runs BugKit's
`symbolicate.sh` (bug-kit PR #10) over the dSYMs of the last `just build-device`, by UUID. A Debug build's code is
`ExerciseAnalyzer.debug.dylib` inside the .app (the main binary is a stub), which is what the payload names, so
Debug builds make dSYMs too (`DEBUG_INFORMATION_FORMAT = dwarf-with-dsym` at the project level: one for the stub,
one for the dylib, one per extension); each frame's offset counts from the binary's `__TEXT` start, which the script
passes to `atos -l` (`-l 0x0` resolves nothing for a binary whose text starts at 0x100000000). System frames print
as offsets; frames from another build print "(no dSYM)" (match the report's `commit`, rebuild it, point `PRODUCTS`
at its products folder). The phone's own
`.ips` reports are a second source: `just pull-crashes` uses libimobiledevice and needs the phone paired over USB.

A session log that simply stops mid-work is the other crash signature: the last events say what was running. A
crash with no MetricKit diagnostic and no `signal-*.txt` from the handler is a kill from outside the process,
most often the memory limit (SIGKILL, uncatchable): read `offline_progress` for the footprint climb, and confirm
with `just trace-device` (Allocations). First crashes caught this way: the detector's output tensor is Float16 on
the phone and was read as Float32; then an export with a data-dependent NMS output (#43).
